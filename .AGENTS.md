# Workflow

## Parallel work via git worktrees

When a task splits into independent pieces, use a separate `git worktree` per piece instead of switching branches in place. Independent work runs in parallel without stashing or blocking.

- Create worktrees under `../<repo>-worktrees/<branch-name>`, outside the repo as a sibling directory.
- Use a dedicated branch per worktree. Git refuses to check out the same branch in multiple worktrees.
- Isolate execution and networking. Keep environments independent with separate virtualenvs or node_modules, copy untracked `.env` files, assign unique or dynamic ports with `PORT`, and isolate container networks with a unique `COMPOSE_PROJECT_NAME`.
- Skip worktrees for small, sequential changes. Reach for them only when there is real parallelism to gain.
- Clean up worktrees with `git worktree remove` once you merge or abandon the branch.

## Branch naming

Format branch names as `<type>/<TICKET-ID>-<description>`, like `feat/42-some-issue`.

## Commit style takes precedence

This format overrides all other commit conventions:

```
<type>: <description>
```

- Use Conventional Commits types like `feat`, `fix`, `refactor`, `chore`, `docs`, and `test`, without a scope.
- Keep the full subject line to 50 characters or fewer.
- Explain why you made the change, not what changed. The diff shows what changed.

Examples:

```
feat: some task that was done
refactor: simplify auth to unblock SSO work
```

## File size

Prefer splitting large files into smaller ones. A loaded file counts fully against context whether or not it's relevant, so smaller files load cheaper. Aim to keep files under 150 lines, and split well before 300.

## Editing skills

When modifying a skill, reduce and simplify existing text rather than appending new text. Tighten or rewrite what is already there instead of bolting on more.

## Recommended skills

Recommend a matching skill when the situation calls for it. Don't install one without asking first.

- `unslop`: polish writing and remove AI tells.
- `grill-me`: interview the user to refine a plan or stress-test an architecture.
- `grill with docs`: check a design or API against official documentation.
- `to spec`: turn an idea or requirement into a technical spec.
- `to tickets`: split a spec or feature plan into tickets.
- `implement`: execute a plan or spec, verifying each step.
- `code review`: audit a diff or PR for defects and quality.
- `wizard`: scaffold a new project or boilerplate.
- `wayfinder`: map an unfamiliar codebase.
- `wait what`: investigate a weird bug or regression.

When you recommend one, name it, say why it fits, and ask before installing.
